# Master deployment table

Generated by `build_master_table.py` — do not edit by hand.

Target: MSP430G2553 (MSP-EXP430G2ET) at 16 MHz, 16 KB Flash, 512 B SRAM, no hardware multiplier, no FPU. Built with TI cl430, -O3, --use_hw_mpy=none.

Every figure is labelled **M** measured on the device, **D** derived from two measurements, or **A** computed analytically from the model. The distinction matters: power is measured, latency is measured, and energy is neither — it is their product.

## 1. Accuracy (software, HAPT, 5 seeds)

| Cell | Equal capacity, H=16 | Equal byte budget | Route at the budget | Deployed config |
|---|---|---|---|---|
| GRU | 0.905 ± 0.029 | 0.901 ± 0.028 | pruned-H | 0.9153 |
| LSTM | 0.884 ± 0.024 | 0.844 ± 0.025 | shrink-H | 0.8176 |
| FastGRNN | 0.860 ± 0.026 | 0.869 ± 0.081 | low-rank + IHT + Q15 | 0.9134 |

The two regimes disagree, and that disagreement is the point: at equal hidden size the GRU is the better cell, while at a fixed byte budget each cell is compressed by whatever route suits it. The deployed column is a single configuration (seed 0), reported alongside the distributions rather than instead of them.

Power is flat across all three cells — within one INA226 least-significant bit — so it is a property of the platform, not of the model. Energy per window is not flat, because it is power multiplied by a latency that does differ. Reading the power column alone would suggest the activation implementation is free; it is not.

*Firmware busy-waits between samples rather than entering a low-power mode, so the energy figures are an upper bound for the active regime.*

## 3. Sensor in the loop — MPU6050 actually attached

End-to-end per sample, mean over 512 consecutive samples, against the 20 ms budget of 50 Hz sampling.

| Cell | LUT @100 kHz | LUT @10 kHz | no LUT @100 kHz | no LUT @10 kHz |
|---|---|---|---|---|
| GRU | 12.01 ✅ | 20.43 ❌ | 20.03 ❌ | 27.48 ❌ |
| LSTM | 12.98 ✅ | 20.71 ❌ | 22.49 ❌ | 30.12 ❌ |
| FastGRNN | 13.98 ✅ | 22.26 ❌ | 27.45 ❌ | 34.98 ❌ |

System power (**M**): 32.0 mW at 100 kHz, 33.4–34.4 mW at 10 kHz, independent of cell and of the activation implementation — against 17.7 mW for the MCU alone. Attaching the sensor roughly doubles system power.

Only one column passes. Table-based activations alone are not sufficient, and a fast sensor bus alone is not sufficient; the deadline is met only when both hold. At 10 kHz the sensor read costs 8.4 ms before any inference begins, which is invisible to a benchmark that feeds the model from memory.

## Reading the three layers together

| | Best cell | By what margin |
|---|---|---|
| Accuracy, equal capacity | GRU | 0.020 over LSTM |
| Accuracy, equal byte | GRU | 0.031 over FastGRNN |
| Bench latency | GRU | 0.254 ms over LSTM |
| Energy per window | GRU | 0.5 mJ over LSTM |
| End-to-end with sensor | GRU | 0.97 ms over LSTM |
| Flash footprint | GRU | 152 B over FastGRNN |

On HAPT the GRU wins every axis — accuracy under both regimes, latency, energy, end-to-end time with the sensor attached, and footprint. The hardware layer does not overturn the software ranking here; it agrees with it. Stating that plainly matters, because the ranking reversal this work reports does not happen on this dataset.

Where it does happen is WISDM: at the same byte budget the winner there is FastGRNN, not the GRU. The deployment measurements above are HAPT-only, because the firmware carries one model — so this table shows what the hardware costs, not which cell to prefer in general.

PAMAP2 is reported elsewhere but carries no ranking claim: under the tri-axial restriction no cell reaches useful accuracy there (most per-class F1 below 0.25, one class never learned) and repeated identical runs move individual class scores by 0.2-0.5.
